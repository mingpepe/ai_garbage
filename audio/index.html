音訊格式設計原理與播放管線 (WAV vs AAC)

0. 整體概念：容器 (Container) vs 編碼 (Codec)

  • 編碼 (Codec)：決定聲音如何用位元表示（例如未壓縮的 PCM、有損壓縮的 AAC）。
  • 容器 (Container)：決定檔案如何組織資料與中繼資訊（例如 RIFF/WAVE、MP4/M4A、或無容器的 ADTS 串流）。

1. WAV (RIFF/WAVE) — 為什麼這樣設計？

  • 設計目標：極簡、無損、隨機存取 O(1)。
  • Chunk 積木架構 (ID + Size + Data)：允許向前/向後相容。若未來新增 LIST/INFO 或 bext 等區塊，舊播放器遇到不認識的 ID 只要讀取 Size 就能整塊跳過，不會解析崩潰。
  • Little-Endian (小端序)：源自 x86 / Windows 生態系，CPU 可直接映射記憶體位元組為整數。
  • 線性時間定位：因未壓縮且每個取樣點大小固定 (BlockAlign)，跳轉至第 t 秒只需精確乘法：ByteOffset = dataStart + floor(t * SampleRate) * BlockAlign。

2. AAC — 為什麼有 ADTS 與 MP4/M4A 兩種設計？

  • VBR 可變長度本質：AAC 透過 MDCT 將波形轉為頻域係數、丟棄人耳被遮蔽的頻段，再用 Huffman 壓縮。複雜片段需要較多 bits、安靜片段極少，因此每個 Frame 長度不同，無法用乘法直接算位址。
  • ADTS (.aac 裸串流)：為網路廣播 / 即時串流設計。無全域檔頭，每個 Frame 自帶 7-byte (或 9-byte) 0xFFF Header，斷線重連或從中間切入都能重新同步，但每個 Frame 重複攜帶標頭且 Seek 需從頭掃描。
  • MP4 / M4A (ftyp + moov + mdat)：為本地儲存 / 快速 Seek 設計。將共通設定抽到 moov > ... > esds (AudioSpecificConfig)，將每個 Frame 的長度與偏移寫進 stsz / stco 索引表，mdat 只放純裸 AAC Access Unit，省去重複標頭並支援查表快速 Seek。

3. Payload 怎麼播放？是直接傳給音效卡嗎？

  • 不是直接傳給音效卡！音效卡上的 DAC (數位類比轉換器) 只看得懂固定取樣率、固定位元深度的線性 PCM 數字，看不懂檔頭也看不懂壓縮資料。
  • WAV (PCM) 路徑：解析 fmt 取得取樣率與位元深度後，data 內的 Payload 本身就是 PCM，經作業系統混音器 (如 Windows WASAPI) 轉換後直接寫入音效卡 DMA Ring Buffer，由 DAC 轉成類比電壓推動喇叭。
  • AAC (ADTS / MP4) 路徑：
    1. Demux (解封裝)：依 ADTS 0xFFF 或 MP4 stco/stsz 切出單一 AAC Frame。
    2. Decode (解碼)：經 Huffman 解碼 → 反量化 → IMDCT 轉回時域，每個 Frame 固定產出 1024 個 PCM 樣本。
    3. 輸出硬體：解碼後的 PCM 樣本才送入 OS 混音器與音效卡 DMA Buffer 給 DAC 播放。
  • 本 Web App 運作方式：瀏覽器透過 AudioContext.decodeAudioData() 在背景將檔案解碼為 32-bit Float PCM (AudioBuffer) 播放，同時本工具依目前播放時間 t 反查對應的位元組區間，即時高亮於右側 Hex Viewer。
